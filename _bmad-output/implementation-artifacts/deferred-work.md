## Deferred from: code review of 4-5-unverified-login-message (2026-07-26)

- **Any login 401 destroys an existing session** [FE/src/shared/api/client.ts:75, FE/src/features/auth/AuthContext.tsx:54-64] — `request()` fires `onUnauthorized()` for *every* 401, auth endpoints included, and `AuthContext` early-returns only when there is no session. `/login` has no authenticated-visitor redirect (`FE/src/app/routes.tsx:52`), so a signed-in user who opens `/login` (header link, bookmark, second account) and submits failing credentials has their valid session wiped from `localStorage` and is redirected to `/login?returnTo=%2Flogin`; the navigation unmounts the banner, so the failure message may never be read. Pre-existing — it applies identically to the wrong-password 401 that shipped before this story; the new message only makes the lost banner more costly. Closing path: skip `onUnauthorized()` for `/api/auth/*` responses, plus a test that seeds `AUTH_STORAGE_KEY` before submitting.
- **No rate limiting, lockout, or failed-attempt tracking on `/api/auth/login`** [BE/TripPlanner.API/Program.cs] — no `AddRateLimiter` or attempt counter exists anywhere in the solution (the only rate-limit logic is the OpenTripMap client's retry constants). Pre-existing and systemic, but this story raises its value to an attacker: the distinct 401 now confirms a correct password on an unverified account and, combined with register, discloses account existence — at unlimited request volume. Tracked here rather than patched because it belongs to the whole auth surface, not one branch.
- **Duplicate registration silently squats an address, and the register→login pair is an account-existence oracle** [BE/TripPlanner.Application/UseCases/Auth/RegisterUserUseCase.cs:27-30] — register on an existing email returns the generic success and does nothing at all. Two consequences. (1) *Squatting:* an attacker who registers `victim@x.com` before the victim does creates an unverified account with the attacker's password; the victim's own later registration takes the duplicate no-op path, so they get the generic success with no account and no email and can never register or discover why. (2) *Oracle:* because the duplicate path leaves the existing password untouched, logging in with the password the attacker just submitted distinguishes "address was free" (now answers the distinct not-verified message) from "address was taken" (answers the generic message). Surfaced by the 4-5 review and **accepted by user decision on 2026-07-26** — the distinct message and a leak-free login response are mutually exclusive under open registration, so the docs were corrected to record the risk instead. (1) is pre-existing and independent of story 4-5. Closing path for both: a pending-registration model (persist email + hash + token separately and create the `User` only when the link is clicked), which also makes squatting expire harmlessly — but note it would make the story's distinct message unreachable, so it is a redesign of the whole register/verify flow, not a patch.
- **The banner instructs the user to check an inbox that `/login` gives them no way to reach** [FE/src/features/auth/LoginPage.tsx:78-96] — the alert is inert and the only footer link is `/register`. The resend flow exists and is anonymous-reachable at `/verify-email` in its token-less idle state (`FE/src/features/auth/VerifyEmailPage.tsx:119-171`), but nothing links to it from the failure the user just hit. Verification tokens expire, so a user who returns days later gets a correctly-named dead end: the mailed link is rejected as expired, re-registering silently no-ops as a duplicate, and there is no route to resend from `/login`. Explicitly out of scope by the approved option for this story ("no inline Resend verification email action"); the distinct message is a strict improvement over the generic one either way. Closing path: render a `<Link to="/verify-email">` when the 401 detail is the not-verified message.

## Deferred from: code review of 6-5-destination-opening-hours-source (2026-07-28)

- **A Redis outage turns the attractions list into a 500 instead of degrading to no thumbnails** [BE/TripPlanner.Infrastructure/Caching/RedisResponseCache.cs:12,35] — `RedisResponseCache` does not guard `GetStringAsync`/`SetStringAsync`, so an unreachable or timing-out Redis surfaces as `RedisConnectionException`/`RedisTimeoutException`. Pre-existing: the 6-5 review flagged this as newly introduced by `WikipediaImageProvider` gaining a cache dependency, but `OpenTripMapPlaceClient` already used `IResponseCache` inside the *same* `try` with the *same* narrow filter before commit `8146a05`, so the exposure predates this story.
