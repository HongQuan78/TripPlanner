### Findings summary (actionable, High → Low)

1. **⚠️ US2-AC2 multi-photo swipe unreachable (Medium priority US)** — the hero gallery fully supports prev/next, arrow-key nav and dots for `total > 1` (`AttractionHero.tsx:34-45,102-131`), but `OpenTripMapDestinationDetailsService` caps `ImageUrls` at a single Wikipedia image (`:27`), so the multi-photo path never activates. Note this is **not** merely a provider accident: `epic-2:55-56` specs the details DTO as carrying an "ordered list of image URLs", so multi-image was documented design intent and the single-image cap is an implementation shortfall against it. *Fix options:* (a) source additional images (Wikipedia `page/media-list`, Wikimedia Commons, or OTM `preview` if it ever becomes usable) to populate >1 URL; or (b) accept the single-image reality and record AC2 as a documented deviation **against the epic as well as the sheet**. → **story `8-5-destination-details-multiple-images` already drafted (`ready-for-dev`)**. Only non-PASS item left in selected *functional* scope.
2. **⚠️ NFR3 cold-open latency is unbounded relative to the 2 s budget, and the mandatory OTM leg dominates it (High priority NFR)** — the enrichment legs are already concurrent (`OpenTripMapDestinationDetailsService.cs:19-24,26,29`) and all three legs cache for 24 h, so **the warm path is fine and there is nothing left to parallelize**. The real exposure is on the cold path, and it is not primarily the enrichment legs: (a) the *serial, mandatory, non-degradable* OTM place fetch defaults to a **5000 ms** timeout (`OpenTripMapSettings.cs:8`) and retries HTTP 429 twice at 600 ms (`OpenTripMapPlaceClient.cs:14-16,40-52`), so that leg alone can consume ~16.2 s before anything else starts; (b) the image leg is **serial internally** — Wikipedia summary, then Wikidata `P18` only if the summary is blank, both on one 5000 ms client (`WikipediaSettings.cs:7`, `WikipediaImageProvider.cs:34-37`) — worth up to 10 s, not 5 s; (c) Overpass adds a single 5000 ms call (`OverpassSettings.cs:7`). Cold worst case ≈ 26 s. *Fix (in priority order):* **the enrichment timeouts are the cheap half but not the sufficient half** — tighten Wikipedia and Overpass to fit the budget (e.g. ~800 ms each, since both degrade gracefully to null) **and** bound the mandatory OTM leg, which needs a real budget rather than a 5 s ceiling plus retries: cap total OTM time (timeout ~1200 ms, and either drop the 429 retries on the interactive details path or move them behind a fast-fail), so `t(OTM) + max(t(image), t(hours))` fits 2 s by construction. Then measure p95 under load. **This finding was wrong in both prior passes** (2026-07-24 recommended parallelizing legs that were already concurrent; the first 2026-07-25 pass named only the two enrichment timeouts and omitted the dominant term) — do not accept a "watch item" framing again without the OTM leg quantified.
3. **⚠️ Both enrichment legs negatively cache transient failures for 24 h — Overpass *and* Wikipedia** — `OverpassOpeningHoursProvider.FetchAsync` returns `null` both for "no `opening_hours` tag" and for timeout/5xx/parse failure (`OverpassOpeningHoursProvider.cs:49-66`), and the caller caches that `null` for `CacheMinutes` (default 1440) without distinguishing the two (`:34-37`). One Overpass blip therefore hides real opening hours for 24 h after recovery, silently weakening US4-AC1 — which is why US4-AC1 is graded ✅-with-annotation rather than unqualified. **`WikipediaImageProvider` has the identical defect** (`:39-43`: `cache.SetAsync(..., new ImageCacheEntry { Value = imageUrl }, ...)` stores a failure-produced `null` for 1440 min), so one Wikipedia blip pins "No photo yet" for 24 h and weakens US2-AC1 and its business rule the same way. Note the two are **not** distinguishable by the code today: Overpass frequently answers `200` with empty `elements` and a `"remark": "runtime error: Query timed out"`, which reaches the same `tags is null → return null` path (`:55-59`) as a genuine missing tag. *Fix:* propagate a tri-state (found / confirmed-absent / transient-error) out of both fetchers — including the Overpass `remark` case — and cache only the first two, with a short TTL (or none) on the error path. **Owner: story 6-5** for Overpass; the Wikipedia half belongs with the image-provider owners (8-x family). Carried as deferred code issues.
4. **⚠️ `openNow.ts` collapses to null or mislabels status on common valid `opening_hours` strings** — confirmed failure modes: lunch-break comma ranges (`Mo-Fr 09:00-12:00,13:00-17:00`) collapse the entire result to null because `TIME_RANGE` has no comma alternation (`openNow.ts:16`) and one unparseable sub-token nulls the whole parse (`:111-115`); `PH off` and other non-day tokens null it via `parseDayToken` → empty `days` (`:101-104`); and **any** month/date/dawn-dusk selector (`Dec 25 off`, `Apr-Oct Mo-Su 09:00-19:00`, `sunrise-sunset`, `09:00+`) does the same. Two further wrong-answer modes, worse than collapsing: the result is computed in the **viewer's** timezone rather than the destination's (`:83-84`), so a user in `Asia/Ho_Chi_Minh` sees "Open now" on a Paris museum at 03:00 CEST; and `OpenNowBadge` and the page each call `parseOpenNow` with their own `new Date()` (`DestinationDetailsPage.tsx:18,133`), so the badge and the aside "Status" can disagree in one paint. **Correction vs the earlier draft of this finding:** overnight ranges (`Mo 22:00-02:00`) do **not** vanish the badge — `openNow.ts:58-60` explicitly handles `end < start`; only the post-midnight window is attributed to the wrong day. The hours *string* renders correctly throughout, so US4-AC1's copy is unaffected; the badge is the unreliable part. Pre-existing (5-15/6-5), **owner: the open-now/Overpass code owners** — carried as a deferred code issue.
5. **⚠️ US1 add-to-trip gating implements only half of epic 2's documented design (selected US)** — access is correctly prevented (401 at `RouteExtension.cs:25-29`, login redirect at `AddToTripContext.tsx:23-26`), and `epic-2:63` does sanction the 401 as "the correct API-level translation of the UI-language AC". But the same sentence continues **"A future frontend greys out the button based on its own auth state"**, and the shipped FE never does — `DestinationDetailsPage.tsx:243-245,282-288` render an always-enabled `<button>`. So this deviates from the sheet's literal *"unavailable/unclickable"* **and** from the epic. *Fix (actionable, small, FE-only):* when `AddToTripContext` reports no authenticated user, render both Add-to-Trip controls `disabled` with the existing "Log in to add to your trip" note as their accessible description — closing the sheet's wording and epic-2:63 in one change. Prior passes recorded "*Fix:* none required", which was based on a half-quote of the epic.
