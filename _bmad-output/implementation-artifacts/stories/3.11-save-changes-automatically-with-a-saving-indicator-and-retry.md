# Story 3.11: Save changes automatically with a saving indicator and retry

As a traveller,
I want my edits saved without pressing save, with visible feedback and a way to recover from failure,
So that I never lose planning work.

**Acceptance Criteria:**

**Given** I create a trip, add or remove a destination, or edit trip name/dates
**When** I close and reopen the app
**Then** every one of those changes is still applied

**Given** a change is being saved
**When** the request is in flight
**Then** a saving indicator is visible

**Given** a save fails
**When** the error surfaces
**Then** I see an error message and my unsaved change is retained locally until I retry

- **Fulfils:** FR19
- **Absorbs:** nothing
- **Status:** **partially delivered — the persistence half only.** Every mutation already commits synchronously, so the first criterion holds today. The saving indicator and the local-retention-on-failure behaviour were never built. This is the second genuine gap found in this pass.

## Dev Context

Verified against the working tree, 2026-07-29.

**AC 1 (persistence) — met.** Every trip mutation commits through the unit of work before responding, so nothing depends on an auto-save mechanism to survive a reload.

**AC 2 (saving indicator) — partially met, and unevenly.** `useMutation`'s `isPending` is already consumed to disable controls and show in-flight text in the dialogs — `FE/src/features/trips/AddToTripDialog.tsx:15` derives it from two mutations, `CreateTripDialog.tsx:28` guards on it, and `AddToTripDialog.tsx:69` renders a "Loading your trips…" message. What has no indicator is the trip planner itself: add, remove, reorder and move on `TripPlannerPage` mutate silently. The state needed is already in hand; only the surfacing is missing.

**AC 3 (keep unsaved changes locally until retry) — not met, and the current behaviour is the opposite.** The trip hooks are optimistic with rollback: `FE/src/features/trips/hooks.ts:123-146` snapshots `previousTrip` in `onMutate`, applies the change locally, and on `onError` restores the snapshot — so a failed save **discards** the user's edit rather than retaining it. That is a deliberate, coherent design; it just contradicts this acceptance criterion, which asks for the change to be kept pending a retry.

**Therefore this story is a real design decision, not a coding task.** Optimistic-rollback and retain-for-retry are mutually exclusive on the same mutation. Pick one before implementing:
- Keep rollback and reword the requirement — the sheet marks FR19 `Selected = No`, so amending it is legitimate.
- Or replace rollback with a retry queue, which means every one of the trip mutations changes its error path, plus new UI for the pending/failed state.

Do not start until that is chosen. Note also that the earlier `3-6` review already flagged concurrent-optimistic-rollback baseline pollution as a systemic issue across all trip hooks; a retry queue would land directly on top of it.
