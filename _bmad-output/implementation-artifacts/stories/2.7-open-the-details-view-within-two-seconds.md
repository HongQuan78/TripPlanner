# Story 2.7: Open the details view within two seconds

As a traveller,
I want the details view to appear promptly,
So that opening a place does not feel like a page load.

**Acceptance Criteria:**

**Given** the user opens a destination detail view
**When** the time to display is measured
**Then** it is within 2 seconds

**Given** the details response is assembled from several external providers
**When** independent legs can run concurrently
**Then** they do, rather than accumulating serially

**Given** a details response has been fetched once
**When** it is requested again within its cache window
**Then** it is served from cache rather than re-fetched

**Given** the per-leg provider timeouts are summed
**When** the cold worst case is computed
**Then** it is reconciled against the 2-second budget, so the budget is not asserted while being structurally unreachable

- **Fulfils:** NFR3
- **Absorbs:** `6-4-attraction-detail-caching`, `6-8-destination-details-latency-nfr3`
- **Status:** partially delivered — caching landed; the budget itself remains unproven. The prior verification pass downgraded NFR3 to a warning after finding the cold worst case around 26 seconds, which no amount of caching alone closes.

## Dev Context

Timeout values read from source, 2026-07-29 — the arithmetic below is the whole problem:

| Setting | Value |
| --- | --- |
| `OpenTripMapSettings.TimeoutMilliseconds` | 5000 |
| `OpenTripMapPlaceClient.RateLimitRetryCount` | 2 |
| `OpenTripMapPlaceClient.RateLimitRetryDelay` | 600 ms |
| `OverpassSettings.TimeoutMilliseconds` | 5000 |
| `WikipediaSettings.TimeoutMilliseconds` | 5000 |
| `PhotonSettings.TimeoutMilliseconds` | 5000 |

The OpenTripMap leg alone can consume roughly 16 seconds before it gives up (three attempts at 5 s plus two 600 ms backoffs), and it is **mandatory** — there is no details response without it. The enrichment legs run concurrently with each other, which the earlier audit confirmed, so parallelising them further buys nothing. **The 2-second budget is not reachable on a cold path with these timeouts, no matter how the calls are arranged.**

Consequently this story is not "add caching" — caching already landed via `6-4` and the provider TTLs default to 1440 minutes. The remaining work is a decision plus a measurement:

1. **Decide what the budget applies to.** A warm cache hit almost certainly meets 2 s already. If NFR3 is read as covering the cold path, the per-leg timeouts must come down to roughly 1200 ms and the retry policy must shrink — which trades tail latency for a higher failure rate, since a slow-but-successful provider response becomes a timeout.
2. **Then measure it.** There is no performance harness in `BE/TripPlanner.Tests` (no source file uses `Stopwatch` or measures elapsed time), so today the budget cannot be verified either way. Whatever is chosen in step 1 needs a repeatable measurement, or this story will be re-litigated a fourth time — the audit has already revisited NFR3 three times.

Related: story 1.9 has the same shape for NFR1/NFR2 and no harness either. Building one harness for both is the obvious economy.
