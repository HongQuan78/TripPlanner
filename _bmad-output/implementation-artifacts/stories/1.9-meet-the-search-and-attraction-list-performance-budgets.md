# Story 1.9: Meet the search and attraction-list performance budgets

As a traveller,
I want search and attraction results to arrive quickly,
So that discovery does not feel like waiting on a server.

**Acceptance Criteria:**

**Given** city/country search under normal conditions
**When** 95% of requests are measured
**Then** results return within 500 ms

**Given** an attraction-list request under normal conditions
**When** 95% of requests are measured
**Then** suggestions are displayed within 1000 ms

**Given** the measurement method
**When** the budgets are asserted
**Then** there is a repeatable way to produce the numbers, so the budget is verifiable rather than assumed

- **Fulfils:** NFR1, NFR2
- **Absorbs:** nothing — **this is a genuine gap.** No existing story measures either budget; the closest work is Epic 6's provider caching, which improves latency without ever asserting it.
- **Status:** backlog

## Dev Context

**There is no performance harness in this repository.** No source file under `BE/TripPlanner.Tests` uses `Stopwatch` or measures elapsed time, so neither budget has ever been observed — they are asserted only in the requirements sheet. That absence, not the code, is what makes this story exist.

**What the budgets are up against** (timeouts read from source, 2026-07-29):

- **NFR1, city/country search ≤ 500 ms p95.** Search goes through `PhotonGeocodingService`, whose `PhotonSettings.TimeoutMilliseconds` is 5000 and whose responses cache for 1440 minutes. A cache hit will clear 500 ms comfortably; a cold call to Photon is entirely at the mercy of a third party that can take ten times the budget. So the budget is really a statement about cache behaviour, and the honest first question is whether p95 is measured cold or warm.
- **NFR2, attraction list ≤ 1000 ms p95.** Harder than it looks. The list comes from a `/radius` call plus one `/xid/{xid}` enrichment call **per attraction** — up to 20 of them, fired concurrently but bounded only by the page size. `OpenTripMapSettings.TimeoutMilliseconds` is 5000 with two rate-limit retries at 600 ms in `OpenTripMapPlaceClient`, so a single throttled attraction can hold the whole list past 16 seconds.

**Suggested shape of the work:**

1. Define the measurement first — cold or warm, which percentile, measured at the API boundary or end to end in the browser. Without this the story cannot pass or fail.
2. Build one harness that serves this story and story 2.7 (NFR3), which has the same problem. Two separate harnesses would be waste.
3. Only then decide whether any code needs to change. It is entirely possible both budgets already hold on a warm cache, in which case the deliverable is the evidence, not an optimisation.

**Do not begin by optimising.** The prior NFR3 experience in this repo is instructive: a latency fix was proposed three times against a model of the call graph that turned out to be wrong, and the "parallelise the enrichment legs" fix was eventually found to be a no-op because they already ran concurrently.
