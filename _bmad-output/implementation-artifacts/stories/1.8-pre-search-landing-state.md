# Story 1.8: Pre-search landing state

As a first-time visitor,
I want something useful on the page before I have searched anything,
So that I can start from a suggested city or one of my recent searches instead of a blank input.

**Acceptance Criteria:**

**Given** I open the app and have not searched
**When** the page renders
**Then** I see the hero search entry point, my recent searches from this session when any exist, and a rail of popular city tiles
**And** recent searches are per-session only — they are not persisted across a reload, a new tab or a return visit

**Given** a popular city tile
**When** it renders
**Then** a city photograph is shown over an unconditional gradient underlay
**And** a missing, failed or still-loading image leaves the tile looking correct with no error state

**Given** a popular city tile
**When** I choose it
**Then** the search input is pre-filled and submitted for that city

- **Fulfils:** **no FR** — additive UI beyond the sheet, recorded so the backlog accounts for delivered work
- **Absorbs:** `5-19-landing-page-framed-editorial`, `5-20-popular-search-tile-images`, `5-14-horizon-home-redesign`
- **Status:** in-progress — code-reviewed 2026-07-30, 27 patches applied and verified (368 FE tests pass, lint clean, build succeeds). One outstanding item: `FE/public/images/hero-banner.jpg` must be supplied, or the `url()` layer dropped so the hero is gradient-only per 5-19's original constraint. Vite emits a build warning naming the missing file until then.

### Review Findings

Adversarial code review, 2026-07-29 — 4 layers (blind hunter, edge-case hunter, verification-gap, acceptance auditor) over the landing files at HEAD. 30 findings retained, 3 dismissed.

**Decision:** layer the url over the gradient so the fallback works; the asset itself must still be supplied.

- [x] [Review][Patch] Hero backdrop points at an asset that does not exist, and its gradient fallback is unreachable [FE/src/features/destinations/SearchPage.module.css:20-21] — `background: linear-gradient(...)` is overwritten by `background-image: url('/images/hero-banner.jpg')`. Verified: no `hero-banner.*` and no `images/` directory anywhere in `FE/` (`FE/public` holds only favicons + webmanifest), so the hero 404s unconditionally in dev, in the nginx container and in production, and with the shorthand overwritten rather than layered there is no fallback — only `.heroScrim` paints, a near-solid `--color-on-surface` slab. Resolved by layering both into a single `background-image`. **Still outstanding: `FE/public/images/hero-banner.jpg` does not exist and must be added — until it is, the hero renders the gradient fallback.** Note `--gradient-hero-stand-in` (`FE/src/app/index.css:36-50`) remains referenced by nothing.

**Decision:** in-memory recents are intended; AC1 amended to match rather than adding persistence.

- [x] [Review][Decision] Recent searches are per-session by design — `recentSearches.ts:5` holds `let history` at module scope with no storage backing, so recents survive route changes within a tab but not a reload, a new tab or a return visit. Raised independently by all four review layers against AC1's "when the page renders". Confirmed deliberate on 2026-07-29: AC1 amended above to state recents are per-session, so the spec now matches the implementation and no code change is required. Two consequences are accepted as part of that call: the "Clear recent searches" affordance reads as more durable than it is, and nothing clears the history on logout, so one user's cities remain visible to the next within a single session on a shared machine.

**Decision:** vendor the six images locally and ship a credit notice; this also closes the deferred URL-rot item.
