# Story 2.3: View destination photos

As a traveller,
I want to see photos of the destination,
So that I can judge whether it is worth visiting.

**Acceptance Criteria:**

**Given** the destination has at least one image available
**When** the detail view opens
**Then** the photos are displayed

**Given** the destination has more than one image
**When** I interact with the gallery
**Then** I can move through the photos

**Given** the destination has no image available
**When** the detail view opens
**Then** a placeholder is shown in place of the gallery

**Given** an image is still downloading or fails to load
**When** the gallery renders
**Then** a loading state is shown and a failure degrades to the placeholder rather than an empty frame

**Given** an image already in the browser cache
**When** the view re-renders
**Then** the image appears rather than remaining stuck behind its loading transition

- **Fulfils:** FR8
- **Absorbs:** `8-1-destination-image-wikipedia-fallback`, `8-2-wikipedia-primary-image-provider`, `8-3-fix-missing-destination-images`, `8-4-image-loading-state`, `8-5-destination-details-multiple-images`
- **Status:** partially delivered — `8-5` (multi-image sourcing, which is what makes FR8 AC2 reachable) is tracked `ready-for-dev`; the other four are tracked `review`

## Dev Context

**The `ready-for-dev` status was verified against source (2026-07-29) and is accurate.** This is the one remaining acceptance criterion in the story:

- `BE/TripPlanner.Application/Interfaces/Services/IDestinationImageProvider.cs` declares exactly one method: `Task<string?> GetImageUrlAsync(DestinationImageContext, CancellationToken)` — **singular**, returning at most one URL.
- `BE/TripPlanner.Application/DTOs/Responses/DestinationDetailsResponse.cs:10` already exposes `List<string> ImageUrls`, so the wire contract is a list today — but the port behind it can only ever supply one element.
- **Consequence:** AC 2 ("move through the photos when more than one exists") is structurally unreachable. The frontend gallery already handles more than one image, so this is a backend-only gap; the UI needs no change to benefit.

**Scope of the remaining work**, per the original `8-5-destination-details-multiple-images` artifact: add a list-returning method alongside the existing single-image one (do not replace it — the attraction-list thumbnail path wants exactly one), source multiple photos from Wikipedia's keyless media-list endpoint, and populate `ImageUrls`.

**Two traps recorded in the earlier verification round, worth carrying in:**
- Cache the answer long and the failure short. The Wikipedia leg previously negative-cached failures for 24 hours, which the Feature 2 audit called out; a transient outage must not blank a destination's photos for a day.
- Do not build the cache key without the host. A language-agnostic key collides across language wikis.

**Leave alone:** the attraction-list thumbnail path and the frontend gallery.
