# Story 6.8: Handle provider datasets at scale

As an operator,
I want the system to cope with very large external destination datasets,
So that growth in provider data does not degrade it.

**Acceptance Criteria:**

**Given** the system's handling of external destination records
**When** volume grows to the order the sheet names
**Then** behaviour and response times remain within their budgets

**Given** the claim of scalability
**When** it is asserted
**Then** there is evidence for it

- **Fulfils:** NFR5
- **Absorbs:** nothing — **third genuine gap.** No story has ever addressed NFR5. It is also the least well-specified requirement in the sheet: "millions of destination records" with no throughput, latency or storage figure attached, and the current design deliberately does not persist provider data at all, so it is unclear what would be measured.
- **Status:** backlog — needs specification before it can be implemented

## Dev Context

**This story is not implementable as written, and that is the finding.** NFR5 in `requirement/Sheet1.html` reads in full: *"The system must handle millions of destination records from external APIs."* It carries no throughput figure, no latency target, no storage target, and its `Selected US?` cell is blank.

**The architecture makes the requirement ambiguous rather than merely vague.** Provider data is deliberately **not persisted**. Location search results, attraction lists and destination details are ephemeral DTOs fetched live on every request; only destinations a user actually attaches to a trip become rows in `destinations`. So the system never holds millions of destination records at all — the provider does. Three readings follow, and they imply completely different work:

1. **Pass-through capacity.** The requirement is about not choking on large provider responses — paging, bounded concurrency, no unbounded materialisation. Largely satisfied already (20-item pages, capped enrichment), and the work is a review plus evidence.
2. **Persisted-catalogue capacity.** The requirement assumes the app ingests and stores the provider catalogue. That is a different product: an import pipeline, indexing strategy, and a storage plan. Nothing like it exists, and nothing in the delivered design points that way.
3. **Cache capacity.** The requirement is about the response cache holding a large working set — eviction policy, memory ceiling, key cardinality. Note the earlier `10-1` review left an open finding about the Redis `--maxmemory` ceiling, which is exactly this reading and is currently unaddressed.

**Required before any development:** the owner picks a reading and attaches a number. Until then this story should stay in the backlog rather than being started on an assumption — reading 2 in particular would reverse a deliberate architectural decision, and doing it by accident would be expensive.

Recommend resolving this alongside stories 1.9 and 2.7, since all three are unmeasured NFRs and would share whatever measurement harness gets built.
