# Accessibility Review — tripplanner auth spines

Scope: DESIGN.md + EXPERIENCE.md (workspace `ux-tripplanner-2026-07-15`), reference mock `imports/sign-in-horizon-travel.html`, current implementation in `FE/src/index.css`, `FE/src/pages/AuthForm.module.css`, `FE/src/pages/LoginPage.tsx`, `FE/src/pages/RegisterPage.tsx`, `FE/src/pages/VerifyEmailPage.tsx`. Floor: WCAG 2.2 AA. Note: `.memlog.md` is listed as a source in EXPERIENCE.md frontmatter but does not exist in the workspace; the audit proceeded without it.

## Overall verdict

The spine pair is unusually strong on behavioral accessibility for a planning artifact — labels, autocomplete, focus visibility, live regions, and target sizes are all explicitly committed, and the core text pairings clear AA with wide margins. However, three token-level commitments fail or cannot be guaranteed by math: outline-variant placeholders at 1.70:1, the pending-state button label at 1.70:1 (the only feedback during submit, rendered in an exempt-but-unreadable disabled style), and the hero gradient, whose 80%→0 ramp cannot protect the 18px body line (non-large text, 4.5:1 required) above the very bottom of the panel. The spine also double-signals the password toggle state (changing name + `aria-pressed`) and claims the hero is "decorative to assistive tech" while keeping its copy as real DOM text — both need one-line resolutions before implementation.

## Findings

- **[high]** Placeholder text in `{colors.outline-variant}` (#c1c6d7) on white inputs is 1.70:1 — far below 4.5:1. Placeholders are real text (1.4.3 has no placeholder exemption), and the spine commits "hello@example.com" as visible content (DESIGN.md "Colors", last paragraph; EXPERIENCE.md "Text input"). Low-vision users see empty-looking fields with invisible example text. *Fix:* render placeholders in `{colors.outline}` (#717786, 4.48:1 — still just short of 4.5:1) or better `{colors.on-surface-variant}` at reduced weight; or drop placeholders entirely — the labels already carry the information and "an empty field reads as empty" survives without sub-AA text.
- **[high]** The pending state is invisible to two user groups at once. The button's only feedback is a label swap ("Signing in…") rendered in the disabled style: #ffffff on #c1c6d7 = 1.70:1 (DESIGN.md "Primary button"; EXPERIENCE.md "State Patterns — Pending submit"). WCAG 1.4.3 exempts disabled controls, but here the disabled control is the *sole carrier of status information*, so low-vision users cannot read it — and no `aria-live` mechanism announces the swap, so screen-reader users get nothing either (4.1.3). *Fix:* keep the button visually in its enabled primary style during pending (use `aria-disabled` + submit guard instead of `disabled`), or pair the label swap with a visually-hidden `role="status"` region; reserve the #c1c6d7 wash for truly inert states.
- **[high]** The hero gradient guarantee is mathematically insufficient at the top of the text block (DESIGN.md "Hero panel" / "Elevation & Depth": the overlay "protects white-text contrast over any photograph"). The claim only holds where overlay opacity stays high: over a bright photo pixel, white text passes at 80% opacity (9.17:1) but falls to 3.32:1 at 50% and 2.52:1 at 40%. The reference mock's `from-on-background/80 via-transparent to-transparent` reaches 0% at the panel's vertical midpoint, so a 48px display headline plus an 18px supporting line stacked above the 40px bottom inset extends into the decayed band. Worse, `body-lg` (18px/400, further dimmed to 90% white) is **not** WCAG large text (threshold: 18.66px bold or 24px regular) and needs 4.5:1, not 3:1. *Fix:* specify the minimum overlay opacity at the top edge of the text block (≥65% keeps white body text above 4.5:1 over any photo: 0.65 blend gives ≈5.1:1), e.g. "gradient holds ≥65% opacity through the entire copy block, decaying to 0 only above it"; or drop the supporting line's 90% opacity.
- **[medium]** Password toggle double-signals state (EXPERIENCE.md "Component Patterns — Password input" specifies the accessible name flips "Show password"/"Hide password"; "Accessibility Floor" additionally specifies `aria-pressed`). A name-swapping toggle with `aria-pressed` announces contradictions: "Show password, toggle button, pressed" while the password is hidden. This is the classic double-signal anti-pattern — pick one convention. *Fix:* either fixed name "Show password" + `aria-pressed` reflecting state, or (better for this control) changing name with **no** `aria-pressed`. Delete one of the two sentences.
- **[medium]** Hero "decorative to assistive tech" conflicts with real DOM text (EXPERIENCE.md "Component Patterns — Hero panel" and "Accessibility Floor": "welcome copy present in the DOM but not in the tab order"). Text in the DOM is always exposed to screen readers regardless of tab order; "not in the tab order" only governs keyboard focus. As written, implementers will either ship an exposed `<h2>Welcome Back.</h2>` before the card's `<h1>` (broken heading order, non-decorative) or guess. *Fix:* specify `aria-hidden="true"` on the hero copy container (acceptable — purely promotional, duplicated by nothing interactive) and require the hero headline be a non-heading element (`<p>` or `<div>`), never an `<h2>`.
- **[medium]** The "Verifying your email…" live-region claim is under-specified and the current implementation would not announce (EXPERIENCE.md "Accessibility Floor"; `FE/src/pages/VerifyEmailPage.tsx` lines 58–77 return entirely different element trees per state). An `aria-live` attribute only announces when content changes *inside* a node that persists in the DOM; swapping the whole `<p className={styles.status}>` for a `<p className={styles.success}>` (or unmounting the section) announces nothing. *Fix:* spine should require one persistent `role="status"`/`aria-live="polite"` container across verifying → verified/failed whose *children* change; failure resolution may instead use the `role="alert"` banner since alerts announce on insertion.
- **[medium]** Spine's ARIA commitments are absent from the current implementation — verify at build time (all three pages). `LoginPage.tsx:67`, `RegisterPage.tsx:74,88,90`, `VerifyEmailPage.tsx:82,103` render error/success text as bare `<p>` with no `role="alert"`/`aria-live`; no `aria-describedby` links field errors to inputs; no `aria-invalid`; the pending button keeps its idle label ("Log in", not "Signing in…"). The spine's claims (Accessibility Floor bullets 2–3) are correct as a contract but currently 0% implemented — nothing in the spine flags this delta. *Fix:* add an implementation-note that every Accessibility Floor bullet is net-new work, not existing behavior, so it lands in story acceptance criteria.
- **[medium]** Input border #c1c6d7 on white is 1.70:1, below the 3:1 non-text component-boundary expectation of 1.4.11. The field remains identifiable via its label, leading icon, and 3rem height, so this is arguably a "boundary not required" case, but the fill and background are both white, making the border the *only* visual boundary of an empty field. *Fix:* darken the input border one step to `{colors.outline}` (#717786, 4.48:1) or accept and document the exception explicitly; do not silently inherit it.
- **[low]** Button/link hover #0070eb with white text passes by 0.15 (4.65:1); the same hover as link text on background #f8f9ff fails at 4.42:1 (DESIGN.md "Primary Container", "Cross-link footer"). The spine only places links on the white card, where hover passes — but any future reuse of the `hover → primary-container` link recipe on the #f8f9ff canvas fails. *Fix:* add a Don't: "primary-container as text color only on `#ffffff`, never on `{colors.background}`."
- **[low]** Reference mock suppresses focus on the visibility toggle (`focus:outline-none`, `imports/sign-in-horizon-travel.html:152`) with no replacement ring — a direct 2.4.7 failure if copied. The spine correctly says focus is "never suppressed"; flag so the mock is not treated as authoritative here. *Fix:* implementation note: the mock's toggle focus handling is a defect, use the standard 2px `{colors.primary}` outline.
- **[low]** "The card has no scroll; if content cannot fit, the content is wrong" (DESIGN.md "Layout & Spacing") can conflict with 1.4.12 text spacing: user-applied line-height 1.5 / paragraph spacing 2em legitimately grows content (error banner + helper + two field errors on Register). Fixed 3rem input/button heights are fine (1.5×16px value text fits), but a hard no-scroll rule plus grown text risks clipping. *Fix:* rephrase as "no internal scroll at default text spacing; the card grows (page scrolls) rather than clips under user text-spacing overrides."
- **[low]** Current card CSS has no horizontal gutter at narrow widths (`AuthForm.module.css:1-12`: `margin: 3rem auto` gives 0 side margin below 26rem viewports), so at 320px the card borders touch the viewport edges. The spine's `{spacing.5}` gutter fixes this — carry it through. Reflow itself passes: single column below `md`, no 2D scroll, no content loss.

## Passes worth keeping

- All core text pairings clear AA with room: ink 17.17:1/16.34:1, supporting text 9.30:1 (even at 12px labels), button text 6.73:1, links 6.73:1/6.40:1, error banner 5.00:1, field errors 6.46:1, success banner 5.49:1.
- Input icons at #717786 on white: 4.48:1 against a 3:1 non-text requirement — pass, and correctly marked `aria-hidden` decoration in the spine.
- Focus: 2px #0058bc outline (6.73:1 vs white), token-level, "never suppressed" — 2.4.7 pass; nothing in the layout can obscure focus (2.4.11 pass — no sticky chrome on auth routes).
- Target sizes: 3rem (48px) inputs and buttons exceed both the spine's own 44px floor and 2.5.8's 24px minimum; toggle hit-area floor explicitly specified.
- `autocomplete="email"` / `current-password` / `new-password` specified and already present in all three pages — 1.3.5 pass.
- Anti-enumeration copy is 3.3.1/3.3.3-compliant: "Invalid email or password." identifies the error and names both candidate fields, and 3.3.3's security exception explicitly covers withholding which one — generic copy here is the *correct* AA behavior, not a compromise.
- Validation on submit with focus moved to the first invalid field, errors clearing on edit, no focus theft by banners — a textbook 3.3.1 flow.
- Placeholders never substitute for visible labels; every input has a programmatic `<label>` (spine and all three current pages).
- `prefers-reduced-motion` globally enforced in `FE/src/index.css:81-90` and re-committed by both spines.
- Register password helper "At least 8 characters." shown *before* errors — 3.3.2 instruction provided upfront.
- No modals, no toasts, Enter submits everywhere, `Esc` has nothing to trap — keyboard model is clean by construction.
